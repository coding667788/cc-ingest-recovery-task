我们需要从零开发一个可长期运行的多源商品库存采集服务，供下游读取一致的本地数据。现在只有模拟供应商接口和协议，没有任何采集业务实现。请直接在此仓库实现并验证，交付可运行代码、自动化测试和操作说明。

使用 Windows 原生 Python 3.12 标准库及 SQLite，不使用 Docker、WSL 或外部服务。阅读 task/PROTOCOL.md、task/ACCEPTANCE.md 与 task/task-config.json；它们是本题完整输入，协议中声明的保证可以依赖，未声明的顺序和原子性不可假设。

两个供应商的读取协议不同：alpha 提供固定时点的分页快照和带游标的变更流；beta 只有按键分页的实时列表及独立的增量日志。我们关心的是长时间运行中不丢变更、不会把旧版本写回、也不会在恢复期间向下游暴露半份数据。

请实现以下完整能力：
1. 从空数据库同时初始化两个源，再持续拉取增量。正确衔接全量与增量，处理分页中发生的新增、更新、删除，以及一次分页读取失败后的重试。
2. 保持源之间的身份隔离。正确处理同一逻辑事件多次投递、版本乱序、删除后重建、不同键相同显示时间、游标失效。版本判断依赖源内 epoch 和 revision，不能靠到达顺序或时间字符串覆盖。
3. 采集检查点、物化数据和去重/隔离记录必须具有一致的持久化边界。进程在响应已收到、事务提交前、事务提交后三个窗口被强制结束后，使用同一个数据库重启，最终状态与无故障运行一致。不要声称网络层严格 exactly-once；允许重拉，但有效落库和可观察副作用不能重复。
4. 历史已被截断或上游 epoch 改变时，自动开始安全重建。重建过程中保留上一份已发布数据，完整追平一个有限的上游高水位后，原子替换该源的公开数据、epoch 和检查点。不能先清空旧结果，不能把未完成的新旧两代混在一起。一个源重建不应让另一个源停采。
5. 有界并发、按源退避，遵守 HTTP 429 的 Retry-After；支持临时 503、网络超时、截断响应。单个源不可用时，另一个源应继续推进，不能进行忙循环重试或无限堆积任务。
6. 对合法事件信封中的坏业务字段进行持久化隔离，保留原始记录、原因和定位信息，并继续处理同一页的其他记录。坏信封、无法完整解析的响应或无法确定的提交结果不能当作成功跳过。存在未解决隔离记录时，在状态中明确标识 degraded。
7. 按协议提供稳定的 SQLite 只读视图和 JSON 行日志。支持正常退出、异常重启和指定的单次崩溃注入点；以可运行测试覆盖恢复、重建原子性和源间故障隔离，不能只测纯函数或依赖 sleep 猜时序。

运行入口：python -m syncworker --config task/task-config.json --db runtime/state.sqlite。程序持续运行，输出可核查的源状态、检查点、重试与故障信息；不要求开发网页界面。
